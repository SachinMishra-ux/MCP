🏗️ MCP System Architecture

A comprehensive block diagram and detailed explanation of how the Model Context Protocol (MCP) works — including the Client, Server, and JSON-RPC 2.0 messaging layer.

1. High-Level Block Diagram

The MCP architecture is composed of three primary layers: the Host Environment (where the user and AI model live), the Protocol Layer (JSON-RPC 2.0 messaging over a transport), and the Server Environment (where tools and data live). External databases, APIs, and filesystems are connected to the server.

2. Communication Flow (JSON-RPC 2.0)

Every interaction between the MCP Client and Server follows a strict request → response pattern using JSON-RPC 2.0. The lifecycle has three phases: Initialization, Operation, and Shutdown.

3. Multi-Server Architecture (1 Client : 1 Server)

A single Host Application can connect to multiple MCP Servers simultaneously. Each connection is managed by a dedicated, isolated MCP Client instance. This keeps servers modular — if one server fails, the others are unaffected.

4. Component Deep-Dive

📡 A. MCP Client

The MCP Client is embedded inside the Host Application. It is the protocol-level connector that manages all communication with one specific MCP Server.

Responsibility Description
Session Management Establishes and maintains a stateful connection with one MCP Server
Capability Negotiation Exchanges supported features during initialization handshake
Tool Discovery Calls tools/list to fetch all available tools from the server
Tool Invocation Sends tools/call requests and returns results to the host
Resource Access Calls resources/list and resources/read for passive data
Transport Abstraction Works over stdio (local) or HTTP/SSE (remote) transparently

⚙️ B. MCP Server

The MCP Server is a lightweight service that wraps external systems (APIs, databases, filesystems) into standardized MCP-compatible interfaces. It exposes three types of primitives:

Primitive Type Description
Resources Passive Read-only data (files, logs, DB rows). Provide context to the model.
Prompts Template Pre-defined prompt templates for standardized interactions.
Tools Active Executable functions. The model can call these to perform real actions.

⚡ C. JSON-RPC 2.0 Protocol

MCP uses JSON-RPC 2.0 as its communication protocol. It adds structured messaging semantics on top of plain JSON — including method names, unique id tracking, and standard error handling.

JSON = data format. JSON-RPC 2.0 = a complete communication protocol built on JSON. MCP needs the latter to function reliably between clients and servers.

5. JSON-RPC 2.0 Message Examples

Every MCP interaction is encoded as a JSON-RPC 2.0 message. Here are the key message types:

① Initialize Request (Client → Server)

{
  "jsonrpc": "2.0",
  "id": 0,
  "method": "initialize",
  "params": {
    "protocolVersion": "2023-10-25",
    "capabilities": { "roots": {}, "sampling": {} },
    "implementation": { "name": "Claude-Desktop", "version": "1.0.0" }
  }
}

② Tool Call Request (Client → Server)

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "San Francisco" }
  }
}

③ Tool Call Response (Server → Client)

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      { "type": "text", "text": "Current weather: 65°F, Sunny" }
    ]
  }
}

④ Error Response

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}

6. Transport Mechanisms

MCP is transport-agnostic — the same JSON-RPC 2.0 messages are used regardless of the underlying transport.
